# Explanation of the Cambridge Runtime and Libraries

*Cambridge BCPL Programming System for MVS 3.8J*

This manual explains how programs obtain execution services and reusable routines. See the [runtime and library reference](Reference-for-the-Cambridge-Runtime-and-Libraries.md) for interfaces and qualifications, and the [compiler explanation](Explanation-of-BCPL-Compilers.md) for translation and execution paths. Native development acceptance is distinct from RC4 distribution acceptance.

## 1. Logical taxonomy and physical modules

The [project nomenclature](../../packaging/architecture/runtime-and-library-nomenclature.md) separates what a component does from how MVS packages it.

| Logical facility | Responsibility | Representative implementation |
| --- | --- | --- |
| Core Runtime | Mandatory execution machinery and fundamental services | BCPLMAIN, BCPLIO, BCPLMEM, BCPLBYTE, BCPLAPT; registration and coroutine bridge |
| Base Library | Recovered historical BCPL-coded services | BLIB |
| Coroutine Support Library | BCPL cooperative lifecycle and transfer routines | COROUTIN, cooperating with Core Runtime BCPLCO |
| System Extensions | Selectable platform facilities or reference extension | BCPLDEMO, BCPLTIME, BCPLQSAM |
| Standard Libraries | Optional portable reusable application facilities | MR10-local helpers exist; native general-purpose library design remains prospective |
| User/Site Libraries | Programmer/site-owned reusable facilities | Individually compiled and selected modules |

The **Cambridge Runtime Library** means Core Runtime plus Base Library. **Cambridge Runtime and Libraries** includes the broader collection. Neither expression names a single PDS. Sharing an object PDS does not make two facilities the same logical library.

A header, a BCPL source unit, a relocatable object and an MVS load module are different artifacts. LIBHDR declares names and numbers; a compiled application uses those numbers; startup must install addresses or data in the global vector. IEWL selection alone does not ensure a BCPL global is installed.

## 2. Core Runtime — startup, entry, globals, calling convention, stack and termination

The native application generated by CG370 is assembled and link-edited with the required runtime objects. Its entry connects to BCPLMAIN. Startup obtains storage, establishes the global and workspace vectors, imports application and BLIB export trailers, installs native service entries, initializes I/O and selected packages, and transfers to START.

BCPL uses numbered global words as rendezvous points across separately compiled units. The native global base is R12, so slot N is addressed at byte displacement 4*N. Application code uses the BCPL workspace in R5 and return linkage in R6, not the ordinary MVS R13/R14 calling convention for every procedure. The system vector in R11 supplies generated-code services such as checked entry.

A checked call receives the complete callee frame requirement as inline metadata. The safe stack limit is not the end of allocated storage: reserved clearance and the published STACKEND have different purposes. An ordinary call may lack a checked-entry guard. Neither a successful compiler run nor stack checking guarantees safe arbitrary pointer operations.

On normal exit, BCPLMAIN runs selected extension finalizers while their streams and allocations are still live, then closes and flushes streams and drains vector allocations before releasing root storage. STOP carries an application status. Exceptional paths can bypass this sequence. See [current BCPLMAIN](../../bootstrap-toolchain/asm/bcplmain.asm) and [historical stack contract](../../packaging/architecture/stack-check-contract.md). The latter describes an older reconstruction, not an exact current or historical implementation.

## 3. Base Library (BLIB) — origins, separate compilation and essential services

The surviving [Cambridge BLIB](../../richards-bcpltape/bcplib/bcpl/blib) is written in BCPL. It uses the historical [LIBHDR](../../richards-bcpltape/sys3/bcpl/libhdr), character and byte primitives, and other runtime state. It contains formatting, string packing, numeric input/output and diagnostic helpers, including procedures that require historical services not yet reconstructed.

The native BLIB object is compiled from the generated derivative of this historical source, rather than a duplicate hand-maintained library. It is linked separately and its exports are registered by BCPLMAIN. The MR10 BLIBI is a different interpreted artifact.

An example from [native regression 075](../../tests/bootstrap/075-blib-writef-mixed-object/README.md):

```bcpl
WRITEF("C:%C S:%S N:%N", 'Z', "HI", 42)
```

The expected output is `C:Z S:HI N:42`. An early run returned the wrong third argument even with successful MVS step RCs. The subsequent correction preserved the actual BLIB G!76 export instead of shadowing it with the provisional runtime formatter. This illustrates why linking code, installing its globals and checking actual program results are separate requirements.

## 4. Memory, vectors and character streams — ownership and MVS translation

A BCPL pointer addresses a word. A vector of upper bound N contains N+1 words. A local VEC lives within its enclosing workspace; APTOVEC provides a temporary vector for a callback; GETVEC provides independently owned storage until FREEVEC or normal runtime cleanup. These are distinct lifetimes. Native BCPLMEM translates vector allocation into MVS GETMAIN/FREEMAIN and tracks the live allocations; the MR10 helper allocator instead works within an explicitly supplied arena.

BCPLBYTE converts word addresses and byte offsets to actual System/370 byte addresses. A packed string starts with its length byte, not a terminating zero. Byte operations do not translate characters.

BCPLIO converts between the BCPL character stream and MVS sequential fixed records. An FB80 input record is right-trimmed and followed by a synthetic newline. Output collects up to 132 characters and emits a blank-padded FB132 record when WRCH receives numeric 10. Earlier CAMBCOMP emitted 37 for *N, producing the DR.5 RC=12 failures. The owner-approved correction preserves 10 in native character and string literals while keeping ordinary EBCDIC translation. Rebuilt CAMBCOMP and BLIB passed the original application (9502) and independent FB132 and input-boundary probe (9504). Logical newline is not written into the physical FB132 record. Older objects require regeneration; see the [runtime reference](Reference-for-the-Cambridge-Runtime-and-Libraries.md). Thus an input character stream cannot preserve significant trailing record blanks, and the core stream is not a binary-record interface.

The job author allocates a DD; FINDINPUT or FINDOUTPUT opens an existing allocation and returns an opaque handle. Selection is separate from discovery. MVS/QSAM owns record I/O and may abend before returning control. JES2 owns spool routing. BCPLIO cannot promise recovery from arbitrary host failures or certify internal spool bytes. See the [dynamic stream contract](../../packaging/milestones/bcplio-dynamic-stream/BCPLIO-dynamic-runtime-contract.md) and [JCL/QSAM responsibility note](../../packaging/milestones/bcplio-dynamic-stream/BCPLIO-JCL-QSAM-stream-contract.md).

## 5. Coroutine Support Library — cooperative transfers, contexts and lifecycle

Coroutines cooperate by explicitly transferring control. They do not execute concurrently as MVS tasks. Each suspended worker must retain enough context to continue at the precise yield site, including its local variables and nested calls.

The native Coroutine Support Library is deliberately separate from historical BLIB. COROUTIN implements creation, parent ownership, transfer and deletion; BCPLCO implements machine-dependent context switching and registration/revocation. The Core Runtime and BCPLAPT must use the currently active stack limit. A worker stack is independent of the root stack.

The accepted native Approach A/S1 domain is one root plus at most two live registered workers, each with a fixed checked 1024-word stack. Creation establishes a valid first activation; CALLCO transfers an argument to a worker; COWAIT yields to its parent; RESUMECO transfers to an inactive worker with the required parent relationship. Root-controlled deletion of a known-live inactive worker revokes its registration before reclaiming storage. The private descriptor layout is not an application interface.

See the [CO.5 acceptance](../../packaging/milestones/coroutines/co5-formal-acceptance-and-closure-20261116.md) and [CO.6 common behavior contract](../../packaging/milestones/coroutines/co6-common-coroutine-contract-20261116.md). Matching observable interpreted/native results do not require matching internal representations.

## 6. MR10 interpreted runtime comparison — ICINT19, BLIBI/ICLIB and separate global domain

The MR10 compiler and its generated applications execute INTCODE under ICINT19. Historical BLIBI supplies library procedures and reconstructed ICLIB supplies host services. The interpreter owns its program vector, globals and execution state. Its fullword-backed storage nevertheless uses two logical packed bytes per interpreted word, unlike four native bytes per word.

Some historical slots coincide with native Cambridge, but meanings can differ. For example MR10 CHANGECO uses G!6, while Cambridge G!6 is SAVEAREA. MR10's reconstruction-local coroutine and allocator numbers are not the native CO.5 assignments. MR10 string and character routines must be understood in their own character representation.

The [MR10 library](../../mr10-kit-compiler/library/README.md) adds portable helpers in separately compiled units. Its allocator requires HEAPINIT and its coroutine demonstration establishes an MR10 root and arena explicitly. Native programs must not copy that initialization or synthetic interpreter frame. The original manually constructed MR10 fixed-stack fixture remains a genuine failure; the separately named valid-frame variant is not a replacement for that historical evidence.

## 7. System Extensions — optional linkage and registration

System Extensions provide selected facilities beyond the mandatory execution substrate. BCPLQSAM exposes logical records; it does not replace BCPLIO's character translation. BCPLTIME supplies platform time primitives. BCPLDEMO is a supported reference implementation. BCPLDEC remains a proposed facility.

A program declares the assigned dispatcher, selects the required linked object, and relies on startup registration to install its entry in the global vector. The BCEX/BCRG scheme uses IEWL-relocated structures and checks actual ownership; package-local operation numbers are separate from global slots. Allocation of a global is not installation of a package. Finalizers must run before Core Runtime I/O and allocation teardown.

See [R.0 owner ABI decisions](../../packaging/milestones/runtime-extensions/runtime-extensions-r0-owner-abi-decisions.md) and [R.5 acceptance](../../packaging/milestones/runtime-extensions/runtime-extensions-r5-closure-20261024.md). Public extension calls and their individual contracts belong in the System Extensions manual family, not this explanation.

## 8. Standard Libraries and User/Site Libraries — current and proposed scope

The MR10 reconstruction already contains reusable integer, string, character, conversion, memory, line and pseudorandom facilities. They are MR10-local modules with tested examples, not a recovered historical Cambridge Standard Library.

The native library staging directory contains copied helper sources; it does not establish a supported resident native general-purpose library. In particular, its inherited G101–116 assignments require collision reconciliation in the native namespace. The [BCPL Standard Library design discussion](../../packaging/architecture/bsl-scope-and-module-design-20261103.md) is a proposed direction, not a committed API, milestone or release. Independently linked modules are preferred where practical, but general registration for arbitrary BCPL library objects remains a design question.

User/Site Libraries can use compatible source, object and registration mechanisms when established for their particular executable. No universal user global range has been allocated. Consult the [Global Number Registry](../../packaging/architecture/global-number-registry.md), including compiler internals, before assigning names.

The [RC4 companion](../../packaging/distribution/publication/RC4-README.md) defines the distributed scope: MR10 is independently usable; native runtime and libraries are work in progress in that release. The [CO.5](../../packaging/milestones/coroutines/co5-formal-acceptance-and-closure-20261116.md) and [CO.6](../../packaging/milestones/coroutines/co6-formal-acceptance-and-closure-20261116.md) records establish bounded native development acceptance, not a native-running compiler or complete historical compatibility.
