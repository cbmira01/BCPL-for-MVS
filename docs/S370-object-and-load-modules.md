# System/370 Object and MVS Load Module Anatomy

## Purpose

This briefing explains what lies between assembler source and an
executable MVS program. It introduces control sections, external
symbols, relocation, object-module records, linkage editing, and load
modules at an orientation level.

## 1. The build transformation

A simple model is:

``` text
assembler source
      |
      v
assembler
      |
      v
object module
      |
      v
linkage editor
      |
      v
load module in a PDS
      |
      v
MVS loader/program management
      |
      v
executable storage image
```

Each stage solves a different problem.

## 2. Why object modules exist

The assembler cannot always know the final runtime address of
everything.

Separate source modules may define symbols used by one another.
Libraries may supply routines later. The final placement of control
sections may not be decided until link-edit time.

The object module therefore contains:

-   generated bytes;
-   symbol definitions;
-   unresolved external references;
-   relocation information;
-   entry/end information.

It is an intermediate representation designed for the linkage editor.

## 3. Control sections

A **control section**, normally introduced with `CSECT`, is an
independently relocatable unit.

Conceptually:

``` asm
MAIN     CSECT
         ...
```

The assembler assigns locations **relative to the control section**. The
linkage editor later places the CSECT within a load module.

This allows separate modules to be assembled without knowing one
another's final addresses.

## 4. Location counters and relative addresses

Within a CSECT, the assembler maintains a location counter.

If:

``` text
instruction A -> offset 000000
data B        -> offset 000120
routine C     -> offset 000180
```

those offsets describe positions relative to the CSECT's origin.

Relocation makes it possible to place the entire CSECT at, for example,
runtime address `00500000` and adjust address-dependent fields
appropriately.

## 5. External definitions and references

Suppose module A calls `SUBR`, which is defined in module B.

Module A needs to say, effectively:

``` text
I reference external symbol SUBR.
```

Module B needs to say:

``` text
I define external symbol SUBR here.
```

The linkage editor reconciles these statements.

This is the foundation of separately assembled programs and object
libraries.

## 6. The traditional object-deck record families

System/360 and System/370 object modules are commonly described in terms
of several record types. The important orientation-level families are:

-   **ESD** --- External Symbol Dictionary information;
-   **TXT** --- generated text (machine code/data);
-   **RLD** --- Relocation Dictionary information;
-   **END** --- end-of-module information.

Think of them as:

``` text
ESD -> what symbols/sections exist or are required?
TXT -> what bytes were generated?
RLD -> which address-sensitive fields must be adjusted?
END -> where does this object module end / what final information applies?
```

The exact card/record layouts are a deeper research topic.

## 7. ESD: describing the symbolic world

The ESD represents entities relevant outside a single local assembly
context, including control sections and external symbol relationships.

The linkage editor uses this information to build a combined symbol
picture across all input modules.

If a link edit reports an unresolved external reference, the problem
lives conceptually in this ESD/symbol-resolution layer.

## 8. TXT: the bytes

TXT records carry the assembled machine instructions and static data.

They do not by themselves make the program executable because some
fields may still depend on where sections are ultimately placed or on
addresses of symbols defined elsewhere.

Thus:

``` text
TXT = generated contents
not
TXT = fully final executable image
```

## 9. RLD: relocation

Consider a fullword in module A intended to contain the address of
`SUBR`.

At assembly time, `SUBR` may be external and its final address unknown.

The object module therefore contains enough relocation information for
the linkage editor to modify the appropriate field once the symbol's
placement is known.

Relocation is what makes independently assembled CSECTs movable.

## 10. END

The END information marks completion of the object module and can
participate in entry-point information according to the object format
and source directives.

Do not confuse:

``` text
assembler END directive
object-module END record
load-module entry point
```

They are related in the build process but belong to different
representations.

## 11. What the linkage editor does

At a high level, the linkage editor:

1.  reads object modules and requested libraries;
2.  collects external definitions and references;
3.  selects additional library modules when needed;
4.  assigns positions to control sections;
5.  resolves external symbols;
6.  performs relocation;
7.  establishes load-module attributes and entry information;
8.  writes a load module to a load library.

This is much more than concatenating object bytes.

## 12. Object library selection

An object library can contain many routines. The linkage editor can
search libraries to satisfy unresolved external references.

Conceptually:

``` text
MAIN references PRINTX
      |
unresolved
      |
search library
      |
member defining PRINTX selected
      |
new references may appear
      |
continue resolution
```

This explains why library order and linkage-editor control can matter.

## 13. Linkage-editor control statements

The linkage editor supports control statements for tasks such as:

-   including modules;
-   specifying names;
-   establishing aliases;
-   selecting entry points;
-   controlling library searches;
-   replacing or changing module relationships.

The exact syntax is a separate topic. The orientation point is that
**object modules are inputs, but control statements tell the linkage
editor how to construct the program**.

## 14. Load modules

The linkage editor's persistent executable result is a **load module**,
traditionally stored as a member of a partitioned data set used as a
load library.

A load module is not simply the original object deck stored under a
different name. It contains the linkage editor's resolved, organized
representation suitable for MVS loading.

Load modules can contain multiple control sections originating from
multiple object modules.

## 15. Entry point

A load module needs an execution entry point.

The entry point may be selected from assembler/object information or
linkage-editor control.

This distinction matters when a module contains several named routines:

``` text
load module
   |
   +-- CSECT A
   +-- CSECT B
   +-- CSECT C

selected entry -> address within one of them
```

If the wrong entry is selected, loading may succeed while execution
begins at the wrong location.

## 16. Relocation at link time and load time

"Relocation" can refer to related adjustments at different stages.

The linkage editor resolves relationships among its input control
sections and external symbols. The loader/program-management machinery
must then make the load module usable at the storage location assigned
during execution.

For orientation, keep the stages separate:

``` text
assembly: section-relative code + relocation requirements
link edit: combine/resolve into load module
load: place executable module into virtual storage for execution
```

Detailed load-module relocation formats are a deeper systems topic.

## 17. CSECT versus load module

A frequent conceptual mistake is to equate one CSECT with one executable
program.

Instead:

``` text
source file may contain one or more CSECTs
object module describes those assembled sections
link edit may combine many object modules/CSECTs
load module is the executable library member
```

The names can coincide, but the objects are not identical.

## 18. Listings and maps

Two artifacts are especially useful:

### Assembler listing

Tells you:

-   offsets within CSECTs;
-   generated instructions/data;
-   symbols;
-   source correspondence.

### Linkage-editor map

Tells you:

-   which CSECTs/modules were included;
-   their placement;
-   external symbol resolution;
-   entry information.

Together they bridge source to the final executable organization.

## 19. A two-module example

Suppose:

``` text
MAIN.ASM defines MAIN
MAIN references ADDONE

ADDONE.ASM defines ADDONE
```

Assembly produces:

``` text
MAIN object:
  ESD: MAIN defined, ADDONE referenced
  TXT: MAIN instructions
  RLD: fields depending on ADDONE

ADDONE object:
  ESD: ADDONE defined
  TXT: ADDONE instructions
```

The linkage editor then:

``` text
places MAIN
places ADDONE
resolves ADDONE
adjusts relocatable fields
selects entry MAIN
writes load module
```

This is the conceptual core of static linking on MVS.

## 20. Why this matters to systems programmers

Understanding object/load structure helps with:

-   unresolved symbols;
-   library construction;
-   language runtime design;
-   compiler back ends;
-   dump interpretation;
-   overlays and module organization;
-   dynamically loaded components;
-   interoperability among separately built modules.

Even when tools hide the details, their diagnostics use this vocabulary.

## 21. Do not confuse the linkage editor with runtime linkage

The word "linkage" appears in two different contexts:

``` text
linkage editor
    -> constructs load modules

program linkage convention
    -> passes control/parameters between executing routines
```

They interact, but they solve different problems.

## 22. Orientation map

``` text
CSECT-relative source
      |
assembler
      |
ESD + TXT + RLD + END
      |
linkage editor
      |
symbol resolution + placement + relocation
      |
load module
      |
MVS loading
      |
runtime storage image
```

## 23. Topics for deeper research

When needed, investigate:

-   exact ESD/TXT/RLD/END layouts;
-   ESD item types;
-   relocation dictionary encoding;
-   `ENTRY`, `EXTRN`, `WXTRN`, and related assembler directives;
-   linkage-editor `INCLUDE`, `ENTRY`, `NAME`, `ALIAS`, and library
    processing;
-   load-module directory entries and attributes;
-   reentrant/reusable module attributes;
-   overlay structures;
-   loader relocation;
-   program fetch and load-library search;
-   object-library management.

The essential model is: **the assembler preserves unresolved placement
and symbol information in an object module; the linkage editor turns a
collection of those modules into an executable MVS load module**.
