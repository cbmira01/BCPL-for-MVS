## Immediate objective

Prove that an ordinary recipient **MVS 3.8J** installation can bootstrap and install the scoped **Cambridge BCPL Programming System** directly from the accepted immutable `BCPL-0.1.0-rc3` / `BC0003` standard-label AWS image, using MVS resident facilities **without Git, WSL, Python, `dspal`, or the development environment on the recipient**.

First demonstrate that `BCPL.BT0001` bootstrap text is readable with ordinary MVS utilities **before BCPL is installed**, and that the `BCPL.BT0002` distribution PDS yields real workable, site-parametric MVS allocation, restoration and verification JCL. Prioritize a bounded MVS-native end-to-end installation path over generating more review or approval scripts.

## Governing acceptance gate

The existing [milestone](milestone-tape-artifact-release.md) defines **TA.3 — MVS Bootstrap and Installation**:

> `BT0001` can be read on a recipient without BCPL; `BT0002` yields operable MVS-only installation jobs; site HLQ/allocation and overwrite policy validated; independently selectable MR10-only, native-only or combined install paths, all without developer tools.

The current approved no-native-compiler candidate declares `native_compiler: absent`; the distinction between *native compiler* and included *native runtime/library/extension* components must be preserved. Validate independently selectable **MR10-only** and **included native-library/extension** profile payloads in the supported configuration; do not imply an executable native compiler or TA.6 PASS. Define the precise available profile mechanics from the existing tape and manifest before implementing any changes.

## Initial work sequence

1. **Read-only inspect and map the actual tape-resident bootstrap.** Confirm which exact installation instructions and JCL are already on `BC0003`, how they use `BCPL.BT0001`/`BT0002`, label sequencing, device type, DCBs, and recipient requirements. Prefer existing saved MVS data and independently inspected original source over restaging or reproducing the tape.
2. **Specify a minimal real MVS-only bootstrap path**, using `IEBGENER` for initial text reading and `IEBCOPY` for restoring the installer PDS, with `IFOX` and `IEWL` as needed for demonstrated programs. Identify where the existing installer template is not yet runnable (site `HLQ`, unit, volume, allocation, target absence/overwrite, profile selection). Discuss genuinely major design choices with the owner; otherwise proceed to code and tests.
3. **Implement recipient-side JCL and instructions** in GitHub-controlled `packaging/`, with exact `BCPL.BTnnnn` mapping from the frozen manifest. Prefer MVS-native checks, a single compact recipient job chain and readable JES evidence over host-only test scaffolding.
4. **Exercise on an isolated clean target** (or clearly isolated previously absent recipient namespace), checking that installation can complete without any developer sidecar in the *recipient* procedure. A separate explicit stateful operation authorization is needed before allocation or destructive changes. Do not consume/recreate accepted TA.2 operation markers.
5. **Confirm actual MVS-installed use** of the distribution through the relevant MR10 and included-native facilities. Distinguish TA.3 bootstrap/installation acceptance from the later full TA.4, TA.5 and TA.7 behavioral gates; reuse accepted verification where sound and do not repeatedly run or request human review without new evidence.
