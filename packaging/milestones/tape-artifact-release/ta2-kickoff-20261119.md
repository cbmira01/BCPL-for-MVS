## Objective and source of authority

TA.2 shall produce, once separately authorized, a **new**
standard-labeled Hercules AWS tape candidate using **one frozen
Git-controlled release manifest** and independently validated
MVS source artifacts. Generated JCL must preserve logical
dataset sequence and correct label/record format; the
producer must have fail-closed no-overwrite/no-retry controls,
independent inventory/restore/readback verification, recorded
SHA-256 and provenance, and immutable artifact handling.

The governing acceptance gate is
[the official milestone](milestone-tape-artifact-release.md)
(section 3, TA.2). Do not renumber TA marches or change
already accepted TA.0/TA.1 outcomes.

## Approved architectural baseline, not yet a frozen candidate

TA.0 provides **20 proposed logical tape datasets**: reserved
`BCPL.BT0001` FB80 human-readable bootstrap and
`BCPL.BT0002` MVS-only installer PDS; 18 selected PDSes
with **127 curated members**, including **79 MR10**.
Positions after the first two are *proposals*, not frozen.
There are **110 Git-backed**, **2 generated**, and
**15 resident binary** members in the provenance worksheet;
path presence is not proof of MVS byte equivalence or
redistribution rights.

There must be one canonical per-candidate manifest in
`packaging/distribution/manifest/releases/` and one
cross-release version/VOLSER registry under
`packaging/distribution/registry/`, derived from the
existing design contract. `config/dspal.yaml` is only a
development dataset map, **not** the release selection.
Logical `BCPL.BTnnnn` aliases and `LABEL=(n,SL)`
are contiguous 1-based dataset positions; these are not
Hercules physical tape file numbers. Source/target PDS
DCBs, sequential IEBCOPY unload DCB, EBCDIC FB80
transformation, and `RECFM=U` load-member preservation
must remain separately modeled.

An accurately disclosed release may have
`native_compiler: absent` and still ship applicable
native runtime/libraries. An `included` candidate requires
the real native-running Cambridge Compiler and its later
TA.6 acceptance evidence; `CAMBCOMP` and MR10 are not
substitutes. MR10-only, native-components-only and combined
dependency closures must remain separate. The installer
and clean recipient tests belong to later marches.

## First TA.2 work — read-only and owner-reviewed design

1. Inspect GitHub `main` and the complete existing
   `packaging/distribution/`, `tools/distribution/` and
   `packaging/distribution/create-tape/` sources, scripts,
   tests and historical MVS/JES evidence contracts. Reuse
   existing mechanisms; do not create a competing manifest
   or tape registry.
2. Reconcile the TA.0 design inventory with exact
   Git-backed member sources and saved MVS source/build
   evidence, source/unload/restored DCBs and unresolved
   generated/binary lineage; **record blockers explicitly**.
3. Present for owner decision the producer architecture,
   manifest freeze and registry identity lifecycle,
   JCL/DASD staging, multiple SL dataset positioning,
   device release/remount behavior, sequencing,
   fail-closed policies and independent verification
   (labels, files, members, content, executable test,
   SHA-256 and provenance).
4. Implement and locally test **pure/offline and read-only
   preflight** scaffolding only after major design choices
   are settled. Check the submitted source and tests
   before commit, keep project docs/JCL under
   `packaging/`, evidence under ignored
   `workarea/`, media under `mvs-state/tape/`,
   and commit approved work to GitHub `main`.
5. Before any production state change, request new
   explicit owner approval of exact source freeze,
   candidate ID/version and **new never-used VOLSER**,
   AWS path, generated MVS JCL, dataset selection,
   operator safeguards and one-shot execution bounds.

## Safety and acceptance boundary

**Not authorized by this kickoff:** reserve a version or
VOLSER; freeze a candidate source SHA; create, initialize,
mount, append, rewind, overwrite or write a new AWS image;
submit state-changing JES; modify MVS datasets; claim
recipient installation or published release; push or tag
a release candidate.

Do not reinitialize or repurpose **BTA101/BTA102**.
They remain accepted TA.1 scratch evidence. Preserve
their SHA-256 identities, raw MVS records and no-retry
receipts. Trust **MVS 3.8J, IFOX, IEWL, IEBCOPY, IEHLIST,
JES and actual BCPL execution** for target-system claims
rather than inferred host-only success.

TA.2 acceptance requires **new candidate media**, frozen
manifest/source identity, exact logical tape order,
independent recorded MVS/Hercules readback, label/filemark
structure, DCB/selected-member/content checks, SHA-256,
provenance and immutable lifecycle. This initial kickoff
does **not** satisfy or authorize that acceptance.
